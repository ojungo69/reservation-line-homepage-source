## 導入制御と配備の制約（2026-11-19）

オーナーの判断は「デザイン改善は確認用環境まで」。一方で、取り込んだ変更は通常どおり本番へ配備し、本番に出していない変更を長く溜めない運用を前提にする。このため、新しいデザインは本番に配備されても表示されないように包み、次のように進める。

- 新しい予定表は、非 secret の環境変数 `ADMIN_CALENDAR_V2_ENABLED` で切り替える。サーバーは `ENVIRONMENT` が `"staging"` または `"local"`（開発者の手元。`/me` が認証なしの開発用管理者を返す環境で、本番では成立しない）で、かつ値が `"true"` のときだけオンと判断する。Wrangler の `--keep-vars` のように以前に設定した値を残す配備では、値が欠落しているだけで本番のオフを保証できないからである。判断の結果は `GET /api/admin/me` で管理画面へ渡し、欠落・不明はオフとして扱う。確認用環境と本番は同じソースから別々にビルドされるので、ビルド時の切り替えにはしない。端末ごとの切り替えも作らない（本番で触れてしまうため）。本番で有効にするのは、オーナーの承認の後に判断の条件を変える別の変更とする。
- 切り替えは、新しいデザインで変える管理画面のすべてに同じ判断で効かせる。予定表だけでなく、`AppShell` の `Header`・`Sidebar` と顧客カルテ（`/customers`）も含む。新しい部品とスタイルはオン側からだけ参照し、共有部品や全体の CSS を書き換えない。切り替えを効かせられない箇所は、別の承認まで変えない。
- オフのときは今の `SchedulePage`・`AppShell`・カルテとそれらのテストを変えない。新しい画面は新しいモジュールに作り、経路（route）と外枠の 1 か所ずつで選ぶ。経路の選択は T000 で、外枠の選択は新しい外枠と一緒に T004b で足す。オフ時の予定表、`/customers` への直接アクセス、予定表とカルテの往復を、経路の試験で固定する（往復の引数と状態の復元は今の `SchedulePage` のテストで確かめる）。今の画面を消すのは、オーナーが本番反映を承認した後とする。
- `wrangler.jsonc` には足さない（欠落はオフ）。手元では Git 管理外の `.dev.vars` に `ADMIN_CALENDAR_V2_ENABLED=true` を書く（既定値は `.env.example` の `false`）。本番で値が欠落していても `"true"` が残っていてもオフになることは、T000 の判定と試験で確かめる。確認用環境でオンにするのは T000b で、新しい予定表を確認用で試せる段階で行う。値は配備側の設定で確認用環境にだけ置き、配備手順書に確認用限定として記載する。止めるときは `"false"` を明示して配備する。T000b では、`"true"` と `"false"` のどちらも承認済みの配備経路と配備後の検証を通って確認用環境に届き、認証済みの `/me` に反映されること、明示の停止の後の通常の再配備でもオフが保たれること、確認用環境の再配備でオンが保たれることを確かめる。
- 開いている画面が切り替えのオフを知るのは、新しい書込の入口が `feature_disabled` を返したときと、`/me` を取り直したとき（画面に戻ったときなど）である。commit送信中か結果不明の操作が残っている間は今の画面へ差し替えず、新しい書込の入口を止めたまま応答を待つ（送信中の操作と結果不明の状態は新しい画面が持ち続ける。停止を知った後に再送するかは、契約の第6章の未決事項で決める）。結果が確定するか（元の commit の成功応答か replay、または最初の要求に対して未適用と確定できる拒否を受けるか。最初の要求でも `write_failed` などの結果不明の応答なら保留を続ける）、スタッフが最新の予約を確かめて結果不明を閉じてから、その時点で最後に確かめた切り替えの状態に従い、今の画面へ戻したことを示して差し替える。結果不明の確定方法は契約の第6章の未決事項で、そのADRのレビューと契約への反映の前に T008〜T010 に着手しない。再読み込みでは照合の状態を引き継がず、その場合は最新の予約で確かめる。
- 各取り込みは確認用環境で確かめてから本番へ配備し、本番で切り替えがオフのままであることを確かめる。
- CSS だけの変更を承認なしで本番へ出す配備でも安全なように、共有トークン（`public/glass-tokens.css`）は新しい名前を足すだけにし、既存の値・素材クラス・今の画面が使うクラスを変えない。デザイントークンの整合テストは拡張だけで、緩めない。
- preview・version 付き commit・変更取消の新しい書き込みの入口は、サーバー側で同じ判断に従わせ、オフのときは副作用の前に拒否する。previewは認可の後に `feature_disabled` を返す。commit（Undo を含む）は、現在の認可の後に成功済みの replay・`idempotency_conflict`・`idempotency_in_progress` は返し、停止の前の操作を照合できるようにする（契約の第4章の手順3、API-25）。これで通常の昇格を続けても、本番では新しい経路から予約・通知・Google 同期が動かない。旧画面の保存はそのまま残す。DB 変更は追加だけで別の PR にし、今の Worker と互換であることを昇格の条件にする。予約の保存は Google カレンダー同期のジョブを積むので、本番で新しい入口を開く前にオーナーへ確認する。
- お客様向けの予約画面はログインの外にあってお客様全員に表示され、CSS の変更がそのまま本番に届き得るため、この切り替えの対象外とする。配色（LINE色を含む）は今のまま、質感・文字・部品だけを揃える。最後に、実装の前にオーナーの承認を取ってから行う。

## 1. 表示・入力の試作で成立条件を確認する

架空データだけで動く試作を作る。週時間軸、スマホの横移動、Macの横wheel、縦スクロール、短い予約、詳細表示、カルテからの復帰を含める。ここでは予約APIへ書き込まない。

実機のiPhone Safari、Android Chrome、Mac Safari・Chromeで確認する。MacのOS設定を変えることを利用条件にしない。慣性入力、画面端、ピンチ、フォーム、リソース列の横スクロールを含める。

長押し後に`touch-action`を変えるだけでは、進行中の指操作を奪えない。初期版は選択後の専用ハンドルを採用する。同じ指で長押しから移動できる方式を試す場合は、通常閲覧のスクロールとズームを保てる実装・実機の証拠を条件にする。

既存構成で入力と描画の要件を満たせない場合に限り、カレンダーまたはジェスチャーの部品を比較する。比較は日本語、制御された日付状態、タッチ、キーボード、仮表示、カスタム予約形状、5分刻み、ライセンス、保守状況、バンドル増を対象にする。候補の現行ドキュメントはContext7と公式資料で確認し、選定理由をADRへ残す。有料部品の購入を実装条件にしない。

## 2. 色と画面構成を段階的に移行する

共有トークンに新しい意味別の色を追加し、旧クラスと各テーマの参照先を確認する。初期段階は新しいカレンダー専用の名前で追加し、切り替えのオン側だけで使う。既存の別名と公開CSSの移行は、承認を得た後の段階で行う。`public/glass-tokens.css`の構造を検証する既存テストを維持し、必要なら新しい契約に合わせて検証内容を拡張する。検証を削除して移行しない。

管理カレンダーを先に適用し、予約詳細、カルテ、公開予約画面へ順に適用する。公開画面のLINE色と既存の予約フローは保つ。ダーク表示、system設定、コントラスト、動きを減らす設定も同時に確認する。

## 3. 週時間軸と閲覧状態を実装する

日・週の座標計算は同じ時刻・時間幅モデルを使う。5分の書込単位と、15分などの表示グリッドを分離する。表示範囲は24時間とし、清掃込みの占有と施術終了を区別する。

閲覧状態は期間、日付、店舗、モード、密度、フィルターを含む。URLへ載せるのは閲覧に必要な非機密値に限定し、個人情報や顧客メモを載せない。スクロールとフォーカスは必要最小限のメモリ状態で復元する。認証主体・店舗権限が変わった場合はキャッシュを破棄する。

隣接期間の先読みは取得権限と既存Queryキーに従う。取得失敗・外部ブロックの上限・部分成功を空きと扱わない。期間移動を完了しても、取得中は新期間の読込表示を出し、旧期間の予約を新日付の下へ表示しない。

## 4. 予約変更のサーバー契約を先に追加する

[提案契約](contracts/reservation-interactions.md)に従い、`/reschedule/preview`と`/reschedule/commit`を追加する。名前とフィールドは提案であり、現行エンドポイントと区別する。

新commitは`expectedVersion`を必須とし、認可、状態、時刻、リソースと顧客のロック、予約行のversion、監査・通知・同期ジョブを原子的に扱う。旧APIは未知のフィールドを無視するため、新UIは旧`/reschedule`へフォールバックしない。対応前のバックエンドで直接操作を有効にしない。

previewは指定した5分刻み・施術時間変更の候補を確認する。現在のavailable-slotsは15分候補と保存済みdurationを使うので、そのままresizeの安全判定へ流用しない。previewは枠を確保せず、commitでも再検証する。

新UIの日時フォームも同じcommit経路へ移す。既存consumerや開きっぱなしの旧画面を調査し、互換期間と再読み込み案内を実装PRで明示する。新契約のversion条件を旧クライアントが黙って無視する構成にしない。

## 5. 直接操作と確認をつなぐ

入力層はタッチ、マウス、wheel、キーボードを扱い、共通の「期間移動」「作成候補」「移動候補」「時間変更候補」を生成する。入力イベントから直接APIへ書き込まない。

候補は元の予約とは別の表示状態に置く。5分へ丸めた時刻と施術・清掃を示し、確認画面で変更前後と通知対象を確認する。保存中・成功・競合・失敗・結果不明を個別に扱う。結果不明のときに、新しい冪等キーで同じ操作を再送しない。

変更取消は、保存成功時の版と変更前値を使う新しい逆変更として実装する。送信済み通知を消せるような表示をしない。Google同期だけが遅延・失敗した場合に、成功した予約保存を見た目だけで取り消さない。

## 6. 段階導入と復旧

仕様の PR（#56）ではランタイム、DB、依存、配備設定を変えなかった。実装は次の順で個別の PR にする。

0. 切り替え `ADMIN_CALENDAR_V2_ENABLED` の判定と、新しい予定表の入口（中身は空でよい）（T000）。
1. 架空データの操作試作と実機結果（オーナーの iPad・iPhone・Mac）。
2. トークン・レイアウト・週時間軸・閲覧ジェスチャー（切り替えがオンのときだけ表示）。確認用で試せる段階になったら、確認用環境で切り替えをオンにする（T000b）。
3. preview・version付きcommitと既存フォームの移行（T003のADRがレビューを通り、契約と受入条件に反映された後）。
4. 移動・時間変更・条件付き取消の公開。
5. カルテ・公開予約・月表示を含む全体の受け入れ確認。

試作の一部を先に公開しても、実装Issue全体を完了扱いにしない。直接操作は既定無効の導入制御を設け、対象端末の受け入れ確認を通過してから有効化する。障害時は直接操作だけを無効にし、新しい競合保護付きフォームを残す。旧APIへの自動フォールバックは復旧手段にしない。

配備は既存の固定SHA採用と段階検証に従う。この文書PRは本番配備やGoogle・LINEへの実データ送信の指示ではない。
