React管理画面と既存のWorkers・Hono・D1 APIを継続する。言語変更やネイティブ化をこの改修の前提にしない。管理カレンダーは現在の自作React構成を基点に、表示、入力、保存の責務を分ける。

## 1. 表示・入力の試作で成立条件を確認する

架空データだけで動く試作を作る。週時間軸、スマホの横移動、Macの横wheel、縦スクロール、短い予約、詳細表示、カルテからの復帰を含める。ここでは予約APIへ書き込まない。

実機のiPhone Safari、Android Chrome、Mac Safari・Chromeで確認する。MacのOS設定を変えることを利用条件にしない。慣性入力、画面端、ピンチ、フォーム、リソース列の横スクロールを含める。

長押し後に`touch-action`を変えるだけでは、進行中の指操作を奪えない。初期版は選択後の専用ハンドルを採用する。同じ指で長押しから移動できる方式を試す場合は、通常閲覧のスクロールとズームを保てる実装・実機の証拠を条件にする。

既存構成で入力と描画の要件を満たせない場合に限り、カレンダーまたはジェスチャーの部品を比較する。比較は日本語、制御された日付状態、タッチ、キーボード、仮表示、カスタム予約形状、5分刻み、ライセンス、保守状況、バンドル増を対象にする。候補の現行ドキュメントはContext7と公式資料で確認し、選定理由をADRへ残す。有料部品の購入を実装条件にしない。

## 2. 色と画面構成を段階的に移行する

共有トークンに新しい意味別の色を追加し、旧クラスと各テーマの参照先を確認する。`public/glass-tokens.css`の構造を検証する既存テストを維持し、必要なら新しい契約に合わせて検証内容を拡張する。検証を削除して移行しない。

管理カレンダーを先に適用し、予約詳細、カルテ、公開予約画面へ順に適用する。公開画面のLINE色と既存の予約フローは保つ。ダーク表示、system設定、コントラスト、動きを減らす設定も同時に確認する。

## 3. 週時間軸と閲覧状態を実装する

日・週の座標計算は同じ時刻・時間幅モデルを使う。5分の書込単位と、15分などの表示グリッドを分離する。表示範囲は24時間とし、清掃込みの占有と施術終了を区別する。

閲覧状態は期間、日付、店舗、モード、密度、フィルター、リソースを含む。URLへ載せるのは閲覧に必要な非機密値に限定し、個人情報や顧客メモを載せない。スクロールとフォーカスは必要最小限のメモリ状態で復元する。認証主体・店舗権限が変わった場合はキャッシュを破棄する。

隣接期間の先読みは取得権限と既存Queryキーに従う。取得失敗・外部ブロックの上限・部分成功を空きと扱わない。期間移動を完了しても、取得中は新期間の読込表示を出し、旧期間の予約を新日付の下へ表示しない。

## 4. 予約変更のサーバー契約を先に追加する

[提案契約](contracts/reservation-interactions.md)に従い、`/reschedule/preview`と`/reschedule/commit`を追加する。名前とフィールドは提案であり、現行エンドポイントと区別する。

新commitは`expectedVersion`を必須とし、認可、状態、時刻、リソースと顧客のロック、予約行のversion、監査・通知・同期ジョブを原子的に扱う。旧APIは未知のフィールドを無視するため、新UIは旧`/reschedule`へフォールバックしない。対応前のバックエンドで直接操作を有効にしない。

previewは指定した5分刻み・施術時間変更の候補を確認する。現在のavailable-slotsは15分候補と保存済みdurationを使うので、そのままresizeの安全判定へ流用しない。previewは枠を確保せず、commitでも再検証する。

新UIの日時フォームも同じcommit経路へ移す。既存consumerや開きっぱなしの旧画面を調査し、互換期間と再読み込み案内を実装PRで明示する。新契約のversion条件を旧クライアントが黙って無視する構成にしない。

## 5. 直接操作と確認をつなぐ

入力層はタッチ、マウス、wheel、キーボードを扱い、共通の「期間移動」「作成候補」「移動候補」「時間変更候補」を生成する。入力イベントから直接APIへ書き込まない。

候補は元の予約とは別の表示状態に置く。5分へ丸めた時刻と施術・清掃を示し、確認画面で変更前後と通知対象を確認する。保存中・成功・競合・失敗・結果不明を個別に扱う。結果不明のときに、新しい冪等キーで同じ操作を再送しない。

変更取消は、保存成功時の版と変更前値を使う新しい逆変更として実装する。送信済み通知を消せるような表示をしない。Google同期だけが遅延・失敗した場合に、成功した予約保存を見た目だけで取り消さない。

## 6. 段階導入と復旧

この文書PRではランタイム、DB、依存、配備設定を変更しない。実装は次の順で個別PRにする。

1. 架空データの操作試作と実機結果。
2. トークン・レイアウト・週時間軸・閲覧ジェスチャー。
3. preview・version付きcommitと既存フォームの移行。
4. 移動・時間変更・条件付き取消の公開。
5. カルテ・公開予約・月表示を含む全体の受け入れ確認。

試作の一部を先に公開しても、実装Issue全体を完了扱いにしない。直接操作は既定無効の導入制御を設け、対象端末の受け入れ確認を通過してから有効化する。障害時は直接操作だけを無効にし、新しい競合保護付きフォームを残す。旧APIへの自動フォールバックは復旧手段にしない。

配備は既存の固定SHA採用と段階検証に従う。この文書PRは本番配備やGoogle・LINEへの実データ送信の指示ではない。
