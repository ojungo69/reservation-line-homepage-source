# Research: 管理画面の整理

調べ方: 管理画面を 6 つの範囲に分けて、変えるべき場所・壊れる試験・足す試験・危険を洗い出した。範囲は、作成パネル、ブロック、詳細、一覧と LINE、設定とカルテと Google 連携、CSV の控え。そのあと、別の確認役が地図どうしの食い違いと抜けを調べた。下の決定は、その食い違いを解いた結果。

## 決定 1: リソースの判断を 1 つの純関数にまとめる

- **Decision**: `admin-app/src/lib/store-resources.ts` に `resolveStoreResources(resources, storeId, selectedId = "")` を置く。
  - 戻り値は `kind` で 4 つに分かれ、どれも `resourceId`（送るべき値）を持つ。
  - `unknown`: 設定のデータがまだ無い（読み込み中・最初の取得の失敗）か、店舗が未決定。`resourceId` は空。
  - `none`: 店舗の稼働中の枠が 0。`resourceId` は空。
  - `single`: 稼働中の枠がちょうど 1 つ。`resourceId` はその枠。
  - `multiple`: 2 つ以上。`resourceId` は、選んだ値が稼働中の候補にあるときだけその値、それ以外は空。利用者が選んだ枠が止まって 1 つだけ残ったときの選び直しでも `multiple` を返すので、候補が 1 つのこともある（空き枠の見出しは、送れる枠が 2 つ以上のときだけ出す）。
- **Rationale**: 同じ判断が、作成パネル・ブロック作成・繰り返しブロック・予約の詳細の 4 か所に要る。洗い出しでは、置き場所・名前・場合分けの名前が 3 通りに割れた。1 つにまとめると、試験も 1 か所で済む。長い部品の認知的複雑度も増やさない。
- **Alternatives considered**:
  - 新しい予定表の `components/calendar-v2/columns.ts` の `activeResourceIds` を使う案: id の配列しか返さず名前が無い。新しい予定表の部品に、今の画面が依存することになるので採らない。
  - 部品ごとに書く案: 4 か所で場合分けが食い違う危険があるので採らない。

## 決定 2: 「読み込み済み」はデータで決め、自動で決めた値は state に書き戻さない

- **Decision**: 呼び出し側は、設定のデータがあるときだけ `resources` を渡し、まだ無いとき（読み込み中・最初の取得の失敗）は `undefined` を渡す。
  - 作成パネルと詳細は、設定の応答が `ok` のときのリソースを使う。
  - ブロック作成と繰り返しブロックは `useResourceList` に「読み込み済み」の印を足して使う。
  - 有効な店舗・枠は描画のたびに導き、検査・送信・確認の画面に使う。`useEffect` で state に入れ直さない。変更の有無の判定は、利用者の選んだ値（state）で行う（導いた値と比べると、開いた直後から「変更あり」になる）。
  - 前に読み込めたデータがあれば、取り直しが一時的に失敗しても、そのデータを渡す。予定表は設定を定期的に取り直すので、1 回の失敗で保存を止めると使えなくなる。前のデータで決めた枠は、保存のときにサーバーが確かめる。
- **Rationale**: 読み込み中の印（`isPending`）で判断すると、最初の取得に失敗したときに印が消え、データは空の配列になる。それを「枠が 0 件」と取り違え、誤った案内を出す。導いた値を state に書き戻すと、店舗の切り替えや遅れて届く設定で古い値が残る。前の予約から次の予約を作るときに、停止中の枠が持ち込まれることもある。
- **Alternatives considered**: `useEffect` で 1 件のときに自動で選ぶ案は、上の隙があるので採らない。

## 決定 3: 店舗の欄は、設定の店舗が 1 件のときだけ隠す

- **Decision**: 作成パネルは、設定の店舗が 1 件ならその店舗を有効な店舗として使い、欄を出さない。確認の画面には店舗名を出す。設定の読み込み前は、今どおり欄を出す。
- **Rationale**: 店舗スタッフに返る設定は、自分の店舗だけに絞られている。そのため「店舗が 1 件」は「選べる店舗が 1 つ」と同じで、役割を見る必要が無い。
- **Alternatives considered**: 役割（staff）で判断する案は、役割と店舗の数の 2 つを見ることになり、店舗が 1 つしかないオーナーの場合を落とすので採らない。

## 決定 4: 予約経路の初期値は定数にし、表示名は変えない

- **Decision**: `admin-app/src/lib/reservation-origin.ts` に `DEFAULT_CREATE_ORIGIN = "walk_in"` を置く。作成パネルの初期値・リセット・変更の有無の判定の 3 か所で使う。表示名（「店頭」「minimo」「その他」）と並びは変えない。
- **Rationale**: 変更の有無の判定を直し忘れると、開いた直後から「変更あり」になり、何も入れていないのに閉じる前の破棄確認が出る。表示名は、オーナーに質問したときは「来店」と呼んだが、画面の名前は「店頭」なので、既存のコードに合わせる。
- **Alternatives considered**: 表示名を「来店」に変える案は、詳細とカルテの表示も変わる。頼まれていないので、この整理では採らない。

## 決定 5: 予約の詳細のリソース名は、枠が 1 つでその枠の予約のときだけ隠す

- **Decision**: 詳細パネルは設定を読み、`resolveStoreResources` の結果が `single` で、予約の `resourceId` がその枠のときだけ「リソース」の行を隠す。設定の読み込み中は隠し、最初の取得に失敗したら出す。前に読み込めた設定があれば、その設定で判断する。
  - 開始時刻の変更・長さの変更の画面の説明文と見出しからは、リソース名を無条件に外す。
  - 予約カードと顧客カルテの履歴からも、リソース名を無条件に外す。
- **Rationale**: 停止中の枠に残る予約や、枠が 2 つ以上の店舗の予約は、名前で見分ける必要がある（spec の FR-008）。変更の画面の説明文は、名前が無くても意味が通る。カードとカルテの履歴は、店舗の枠の数を知らないので、条件で出し分けるには余計な取得が要る。
- **Alternatives considered**:
  - 読み込み中に出しておく案: 運用中の店舗はどれも枠が 1 つなので、出てから消えるちらつきになる。採らない。
  - カードに条件を付ける案: 取得が増えるので採らない。

## 決定 6: 名前の変更は画面の文字と文書だけ

- **Decision**:
  - 詳細のボタン: 「時間変更」→「開始時刻を変更」、「施術時間変更」→「長さを変更」。
  - 変更の画面の題名もボタンと同じ名前にする。
  - 送信ボタン: 「この時間に変更」→「この開始時刻に変更」、長さの画面は「この長さに変更」。
  - 完了の通知: 「開始時刻を変更しました」「長さを変更しました」。
  - 量を指す言葉は変えない: 「新しい施術時間（分）」「現在の施術時間」など。
  - spec 008 の文書に出てくる操作の名前も直す。
  - API のパス（`/reschedule` など）とエラーの符号は変えない。
- **Rationale**: 2 つのボタンの違いが名前で分かるようにする。サーバーとの約束は変えない。
- **Alternatives considered**: 2 つの操作を 1 つにまとめる案は、サーバーの約束と通知が変わるので採らない。

## 決定 7: LINE 友だちの紐付けの店舗は、画面が自動で送る

- **Decision**: `admin-app/src/lib/link-store-id.ts` に `pickLinkStoreId(stores, selectedStoreId)` を置く。画面の上で選んでいる店舗が設定にあればそれを、無ければ（全店舗のとき）設定の先頭の店舗を返す。
  - LINE 友だちの画面と、顧客カルテからの紐付けの画面の両方で使い、店舗の選択欄を消す。
  - サーバーの検査（店舗の存在の確認）は変えない。
  - 操作の記録の詳しい情報に残る店舗の意味を、サーバーのコードに 1 行のコメントで書く。
- **Rationale**: サーバーでの店舗の使い道は、存在の確認と、操作の記録の詳しい情報の 2 つだけ。お客様は店舗に属さず、紐付く相手も店舗で変わらない。操作の記録の画面はこの店舗を見せておらず、生の情報を見られるのはシステム管理者だけ。
- **Alternatives considered**: サーバーで店舗を任意にする案は、受け付ける値の検査が変わる（FR-024 に反する）。得るものも小さいので採らない。

## 決定 8: 予約管理の店舗の列・来店中・CSV のボタン

- **Decision**:
  - 予約管理の画面は、表示している店舗が 1 つに決まっているとき（画面の上で店舗を選んでいる、または店舗スタッフ）に、次を出さない: 一覧のカードの店舗名、表の店舗の列、店舗での並べ替え。カードには、出すかどうかを決める属性を足す。既定は「出す」にし、ほかの画面の表示は変えない。
  - 「来店中」は状態の選択肢の一覧から外し、一覧は検索の状態の部品に移す。保存された絞り込み（ブラウザの履歴の中）の状態が選択肢に無いときは、既定に戻す。
  - CSV のボタンと、CSV の URL を作る関数を消す。サーバーの CSV 出力は残す。
- **Rationale**: 店舗が 1 つのとき、店舗名はどの行も同じで読む量を増やすだけ。来店中は、付ける操作が外れていて、選んでも何も出ない。サーバーの CSV 出力は、機械による検証で使う。
- **Alternatives considered**: 来店中の値が入った保存値を、状態だけ既定に戻して残す案。保存値は、ブラウザの戻る操作のときにしか使わない。全体を既定に戻すほうが小さく、spec の「既定の絞り込みで開く」とも合う。

## 決定 9: CSV の控えはコードだけを消す

- **Decision**: 次を消す。
  - 控えを書く部品 `src/storage/r2-helpers.ts` と、その試験 `test/r2-helpers.test.ts`
  - CSV 出力の中の呼び出しと読み込み
  - 使われなくなる型（保管場所のつなぎ込みと、止めるための設定値）
  - 古い設定が残っていても控えを書かないことは、試験で確かめる。
  - CSV 出力の応答（中身・ヘッダー・ファイル名・逐次の送り方）は変えない。
  - 配備の設定ファイル（`wrangler.jsonc`）は変えない。導入の手順書は、保管場所の手順を残したまま、「設定を有効にすると控えを保管する」という説明だけを今の動きに直す（レビューで見つかった食い違い）。
- **Rationale**: 配備と検査の設定ファイルは、ほかの変更と分けて変える決まりになっている。設定のつなぎ込みが残っていても、使うコードが無ければ控えは作られない。導入の手順書の保管場所の手順は、設定が保管場所を求める限り正しい。控えを保管するという説明だけは、コードを取り除くと事実と違うので直す。
- **Alternatives considered**: 設定ファイルも同時に変える案は、ほかの変更と混ざるので採らない。

## 決定 10: 0 件の案内の文

- **Decision**:
  - 手動予約: 「この店舗は予約枠が未設定のため、予約を作成できません。」
  - ブロック作成と繰り返しブロック: 「この店舗は予約枠が未設定です。店舗設定の「リソース」タブで追加してください。」
  - 文はリソースの判断の部品に置き、画面ごとに書き分けない。
- **Rationale**: 手動予約は店舗スタッフも使うが、店舗スタッフはリソースのタブを開けない。ブロックと繰り返しブロックはオーナーだけが使う。

## 確かめた事実（2026-11-20）

- 運用中の店舗は、どれも稼働中の予約枠がちょうど 1 つ。
- 「来店中」の印が付いた予約は、運用中のデータに 1 件も無い。
- 予約経路を書くのは、管理画面の手動予約の作成だけ。管理画面で経路を送るのは作成パネルだけ。
- 物理削除でリソースの行を消す経路は無い。削除の API も行を残して停止（`active = 0`）にするだけ。承認待ち・確定の、開始前の予約がある枠は拒否される。確かめ方は、無効化（更新の API）が稼働中の枠を止めるときだけ、削除の API は停止済みの枠でも確かめる。

## 既存の文書とコードの食い違い（この整理で直す）

- リソースを「削除すると関連する行が連鎖して消える」と書いたコメントが 3 か所と、権限表の説明が 1 か所ある。
  - コメント: `admin-app/src/pages/settings.tsx`、`src/admin/settings-common.ts`、`src/admin/settings-resources.ts`
  - 権限表: `docs/admin-authz-matrix.md`
  - 実際の削除は停止にするだけで、行は消えない。実態に合わせて直す。
- 予約経路の表示名: spec の最初の版は「来店」「Minimo」と書いたが、画面は「店頭」「minimo」。spec を画面に合わせて直した。
- 顧客カルテからの紐付けの画面のコメントは、店舗を「初回の来店記録の店舗」に使うと書いている。この初回の来店記録の仕組みはもう無いので、店舗の選択欄と一緒に消す。
